# ADR-0015 — Cross-Platform Architecture Evidence-First Baseline

**Status:** Accepted baseline  
**Date:** 2026-10-04  
**Scope:** Android, iOS, Windows, macOS, Linux  
**Supersedes:** unverified assumptions that Rust, KMP, Compose Multiplatform, or any specific cross-platform stack is already implemented

## Context

Eagle is intended to be a multi-platform platform targeting Android, iOS, and desktop. The repository must not treat a technology as implemented merely because it appears in planning documents.

The authoritative implementation evidence is:

1. current source code;
2. tests;
3. successful build/verification;
4. proven integration;
5. dependency/version evidence.

## Decision

Eagle adopts an **evidence-first cross-platform architecture**.

The conceptual boundary is:

`Eagle Platform → Shared Core/Application Contracts → Platform Abstraction → Native Platform Integration`

The shared layer must contain only logic whose semantics can be made platform-independent. Security-critical decisions must have identical semantics across supported platforms.

Platform-specific code is allowed for:

- secure key storage;
- OS cryptographic facilities when explicitly approved;
- lifecycle/background execution;
- notifications;
- permissions;
- filesystem/OS integration;
- packaging and signing;
- other APIs that have no safe shared equivalent.

## Current verified implementation

At this ADR's creation, the verified implementation is an Android/JVM Kotlin security foundation under:

`app/src/main/java/com/eagle/app/security/`

Verified components:

- `SessionStateMachine`
- `ReplayGuard`
- `TokenBucket`
- `SecurityEvent`
- `SecurityFeatureExtractor` / `FeatureVector`
- `StatisticalBaseline`

Corresponding unit tests are present under:

`app/src/test/java/com/eagle/app/security/`

This is **not yet a verified cross-platform implementation**.

No Rust Security Core, KMP shared module, iOS application, or desktop application is treated as implemented by this ADR unless source/build/integration evidence is later recorded.

## Technology policy

The following are **candidate technologies, not decisions**, until verified by a dedicated component evaluation:

- Kotlin Multiplatform;
- Compose Multiplatform;
- Rust;
- UniFFI;
- cryptographic libraries;
- networking/mesh frameworks;
- ML frameworks.

A technology may be adopted only after:

`Requirement → Architecture Fit → Security Review → Maintenance/Maturity → Exact Version → License → Tests → Build → Integration → Operational Evidence`

## Cross-platform invariant

For any security-critical core component:

`Same Input → Same Core Semantics → Same Security Decision`

Platform code may change how a decision is executed, displayed, persisted, or integrated with the OS, but must not silently change the security meaning.

## Migration rule

The existing Android security foundation is retained as verified source evidence. It may be refactored into a shared module only after the extracted contracts and dependencies are identified and the resulting shared tests pass.

Migration must be incremental:

1. inventory current code;
2. identify platform-neutral contracts;
3. identify Android-specific dependencies;
4. extract shared contracts;
5. preserve existing tests;
6. add cross-platform test vectors;
7. add one additional platform;
8. verify identical semantics;
9. only then consider broader UI sharing.

## Consequences

Positive:

- prevents architecture documents from becoming false implementation claims;
- keeps security semantics centralized;
- allows Native APIs where they are actually required;
- permits KMP/Rust/Compose or alternatives to be selected from evidence;
- makes future platform expansion auditable.

Costs:

- initial implementation remains Android-first;
- cross-platform extraction requires additional testing;
- some platform-specific duplication is intentional;
- technology selection happens after evidence collection rather than before it.

## Verification gate

A platform is not considered supported until all relevant gates have evidence:

- source implementation;
- build;
- unit tests;
- integration tests;
- security tests;
- platform-specific behavior tests;
- dependency review;
- packaging/signing where applicable;
- CI verification.

## Non-goals

This ADR does not select:

- KMP;
- Compose Multiplatform;
- Rust;
- UniFFI;
- a crypto library;
- a transport/mesh framework;
- an ML framework.

Those remain separate decisions.
