# ADR-0007 — Architecture & Task Baseline v1

**Status:** Proposed  
**Date:** 2026-10-02  
**Deciders:** Pending explicit project approval  
**Related ADRs:** ADR-0001 → ADR-0006  
**Supersedes:** None  
**Superseded by:** None

## Context

The repository already contains ADR-0001 through ADR-0006 and a preliminary architecture document. The current architecture document explicitly states that the final architecture has not yet been settled.

A single planning baseline is therefore needed to define module boundaries, dependency direction, security boundaries, and the distinction between decisions and implementation tasks without prematurely selecting concrete cryptographic, serialization, storage, or transport technologies.

## Decision

**Proposed for acceptance:** adopt Architecture & Task Baseline v1 with these modules:

core, identity, crypto, protocol, storage, mesh, ui, integration, security, observability, documentation.

### Dependency direction

`core` is the contract layer.

- identity → core
- crypto → core + identity contracts
- protocol → core + crypto contracts
- storage → core
- mesh → core + protocol contracts
- ui → core + application services
- integration → implementations for wiring only
- security → read/test/audit
- observability → sanitized contracts

There is no direct storage → protocol dependency and no crypto ↔ mesh circular dependency.

### Security boundary

Send:

`plaintext → crypto → encrypted envelope → protocol → mesh → transport`

Receive:

`transport → mesh → protocol → crypto → plaintext → application/UI`

Therefore mesh and protocol are prohibited from handling application plaintext; storage and UI are prohibited from exposing private keys; logs and telemetry are prohibited from containing plaintext or secrets.

### Decision / implementation separation

ADR documents decisions. Implementation issues execute accepted decisions.

Example:

- ADR-0010 decides serialization.
- PROTO-003 implements that accepted decision.

### Later technical ADRs

The following remain separate decisions and are not preselected by ADR-0007:

- ADR-0009 — Key Management

## Consequences

### Positive

- One explicit architectural reference.
- Clear dependency direction.
- Explicit plaintext/private-key boundaries.
- Clean separation between decisions and implementation.
- Foundation for automated architecture checks.

### Constraints

- Existing ADR-0001 → ADR-0006 must be checked for compatibility before acceptance.
- No technical choice is considered accepted merely because it appears in planning material.
- Implementation issues must not be treated as approved until their governing ADRs and gates are satisfied.

## Alternatives considered

1. Keep the current preliminary architecture unchanged — rejected as insufficiently precise for implementation planning.
2. Put all technical decisions into one baseline ADR — rejected because independent review and revision would be impaired.
3. Select concrete crypto/serialization/storage technologies now — rejected because repository constraints and security review are not yet complete.
