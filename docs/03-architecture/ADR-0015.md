# ADR-0015 — Identity, Device, and Multi-Device Membership

## Status
**Proposed**

- Implementation: Not authorized by this ADR
- Verification: Pending
- Release: Blocked

## Decision baseline
Eagle uses a **Signed Membership Log with Causal Ordering and Policy-Checked Signatures** as the working membership-state model.

This ADR defines membership state and security constraints. It does not select the final multi-device encryption or session/key-agreement mechanism.

## 4.5 Membership Authority and Signer Set
Membership authority is an explicit policy over authorized devices. Enrollment alone does not grant membership-management authority.

Each transition MUST identify the predecessor state, successor state, affected account/device, current Trust Epoch, operation, authorization policy, required signer set, signatures, and freshness/replay protections.

Conceptually:
`SignerSet(state, operation, policy) -> required authorization`

The policy MAY distinguish bootstrap, device addition, device revocation, signer-policy change, and recovery transitions.

An M-of-N quorum is NOT fixed by this ADR. Thresholds and signer policy remain explicit protocol-policy decisions.

Constraints:
- bootstrap uses an explicitly authenticated bootstrap authority;
- device addition and revocation require policy-defined authorization;
- self-revocation MAY be supported only as an explicitly defined emergency transition;
- a device cannot elevate its own authority;
- recovery authority is defined by ADR-0018;
- signer-policy changes require authorization at least as strong as the policy being changed;
- no implicit Primary Device role is created.

## 4.6 Multi-Device Encryption Constraints
The final mechanism is deferred. Any accepted mechanism MUST satisfy:

1. Recipient set equals the authorized recipient-device set at send time.
2. Newly added devices do not receive historical messages by default.
3. Revoked devices cannot establish authorization to receive post-revocation messages.
4. No universal shared account secret enables unrestricted bulk decryption.
5. Ciphertext/message-size amplification is bounded and measurable.
6. Sender does not require all recipient devices online.
7. Authorized recipient devices can decrypt offline after obtaining required protocol state.
8. Forward secrecy and post-compromise security are preserved per device.
9. Replay against an unauthorized/different recipient-device set is rejected.
10. Sender-device identity is cryptographically bound to the authenticated message/ciphertext context.
11. Recipient set derives from a verified membership snapshot, not untrusted infrastructure metadata.
12. Membership changes do not retroactively alter the authenticated recipient set of an accepted message.

These are acceptance constraints, not algorithm selection.

## 9 Trust Epoch Invariants
- **E1:** monotonic within the account membership domain.
- **E2:** advances only through an authenticated membership transition.
- **E3:** cryptographically bound to resulting membership state.
- **E4:** stale verified epochs deny privileged operations unless explicit authenticated reconciliation is in progress under fail-closed rules.
- **E5:** transitions are observable online and verifiable offline.
- **E6:** one device cannot advance the epoch beyond membership-policy authority.
- **E7:** Trust Epoch, session counters, and message counters are independent state machines.
- **E8:** unknown or conflicting epoch state fails closed for privileged operations.

## 10.5 Membership State Model
Membership State is a signed append-only set of membership entries with predecessor binding, causal ordering, monotonic membership version, Trust Epoch binding, and policy-checked signer authorization.

Each entry MUST contain at minimum:
`entry_id`, `account_id`, `predecessor_hashes`, `membership_version`, `trust_epoch`, `operation`, `subject_device_id`, `signer_set`, `signatures`, freshness/expiry information, and `protocol_version`.

State is derived deterministically from valid entries. Entries do not erase predecessors.

### Concurrent branches
Concurrent branches MUST NOT be silently merged.

```
Concurrent branches
        |
        v
Conflict detected
        |
        v
Privileged operations denied
        |
        v
Authenticated reconciliation
        |
        v
Valid successor state
```

Prohibited:
- last-writer-wins;
- silent merge;
- trusting newest wall-clock timestamp;
- accepting a later-arriving branch solely because it arrived later.

Reconciliation MUST be authenticated and produce an unambiguous successor state before privileged membership operations resume.

## Event ownership

| Event | ADR-0015 | ADR-0016 | ADR-0018 |
|---|---|---|---|
| Add device | membership transition + epoch effect | session/key consequences | — |
| Revoke device | membership transition + epoch effect | session invalidation | revocation/recovery consequences |
| Recovery | sensitive transitional state | session consequences | authority + mechanism |
| Session resumption after epoch change | invalid/stale resumption prohibited | execution rule | — |

## Acceptance Authority
Acceptance authority is governed by `docs/00-governance/ADR_AUTHORITY.md`. Until that governance is accepted, ADR-0015 remains Proposed.

## Verification obligations
Before acceptance, explicit test IDs and evidence MUST exist for authorized/unauthorized addition and revocation, self-revocation, concurrent branches, stale/unknown epoch, replay and duplicate entries, signer-policy changes, offline verification, reconciliation, and recipient-set enforcement.

## Non-goals
This ADR does not choose a specific E2EE construction, key-agreement protocol, storage, transport, recovery mechanism, or release approval.
