# ADR-0015 — AI/ML Security Boundary and Adoption Strategy

Status: Proposed
Date: 2026-10-04

## Context
The repository currently contains development-time AI agents for CI repair and provenance documentation, but no verified product AI/ML implementation in the audited main baseline.
Introducing an AI model before defining the event schema, security boundary, evaluation criteria, and fallback behavior would create a new security dependency without a measurable requirement.

## Decision
1. AI/ML is advisory intelligence, not the security authority.
2. Deterministic policy remains authoritative for security enforcement.
3. Product AI consumes sanitized, versioned features rather than unrestricted secrets/private keys.
4. Every model output is auditable through model version, feature schema, and evidence identifiers.
5. Statistical/deterministic baselines precede complex ML.
6. Training and evaluation may use mature offline tooling; mobile inference requires an explicitly approved runtime.
7. LLMs, if introduced, are explanation/recommendation components unless a separate security-reviewed ADR establishes another bounded role.
8. No model or AI agent may silently weaken cryptographic, authentication, authorization, protocol, or test controls.

## Reference pipeline
SecurityEvent -> FeatureExtractor -> Baseline/Model -> Signal -> DeterministicPolicy -> Action
Optional: Signal + minimized evidence -> ExplanationModel -> human/UI explanation

## Rejected approaches
LLM as security decision maker: rejected.
Custom ML framework: rejected until existing maintained runtimes are evaluated and shown insufficient.
Product AI before telemetry: rejected because it cannot be meaningfully validated without a defined event/feature schema and representative data.

## Consequences
Benefits: clear trust boundary, reproducible decisions, replaceable models, lower privacy exposure, easier offline evaluation and incident analysis.
Costs: explicit event schema, model lifecycle, dependency due diligence and initially limited AI scope.

## Required follow-up
Define SecurityEvent, FeatureVector, AnomalySignal, RiskAssessment and model metadata/provenance. Create deterministic baseline tests and an evaluation dataset strategy. Benchmark approved Android runtimes before adding a dependency.
