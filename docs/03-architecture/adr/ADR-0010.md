# ADR-0010 — Serialization

**Status:** Proposed — Decision Pending Review  
**Date:** 2026-10-02  
**Related ADRs:** ADR-0007, ADR-0008, ADR-0009

## Context
Define serialization for encrypted envelopes, packet framing, persisted encrypted records, and protocol metadata. Requirements include compact size, predictable parsing, versioning, schema evolution, Kotlin/Android support, and auditability.

## Candidate formats
- Protocol Buffers: evaluate schema-first evolution, generated code, tooling, size, build complexity, and compatibility.
- CBOR (RFC 8949): evaluate compact encoding, IETF ecosystem alignment, schema/versioning, and Kotlin support.
- MessagePack: evaluate size/performance and compatibility with project governance.
- FlatBuffers: consider only if zero-copy access is demonstrated to be needed.
- Custom binary: exceptional-risk path because parsing, evolution, and compatibility become project-owned responsibilities.

## Decision criteria
Wire size; parsing performance; versioning/evolution; schema validation; Kotlin/Android support; interoperability; auditability; future standards compatibility.

## Decision
Pending review. No serialization format is approved as production-authoritative by this draft.

## Implementation baseline

A bounded CBOR candidate is now implemented in the Rust security core using minicbor 2.3.0, pinned in Cargo.lock. The implemented wire shape is a fixed seven-element CBOR array with definite-length byte strings only.

Security controls:
- bounded total input before parsing;
- fixed field count and field order;
- definite-length arrays and byte strings only;
- exact identifier/payload bounds;
- rejection of trailing bytes;
- canonical re-encoding comparison before acceptance.

This remains an implementation baseline, not final protocol approval. Cross-language compatibility, protocol versioning, authenticated-byte coverage, and independent review remain required.
    
## Security-specialty closure

The serialization boundary must provide schema-defined, versioned, bounded, strictly validated encoding. Canonical byte representation is required wherever authenticated or signed bytes depend on exact representation.

No custom binary format is approved. The concrete production format remains subject to cross-language implementation proof, canonicalization tests, and protocol review.
