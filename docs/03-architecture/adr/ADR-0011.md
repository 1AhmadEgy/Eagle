# ADR-0011 — Local Storage

**Status:** Proposed — Decision Pending Review  
**Date:** 2026-10-04  
**Related ADRs:** ADR-0009, ADR-0010

## Context

Eagle needs a persistence boundary for application records while preserving the Security Kernel boundary around identity and cryptographic material.

The existing planning record does not approve a concrete database, file format, encryption format, backup model, or key-storage implementation. This ADR therefore defines only the architectural contract and deterministic failure semantics.

## Decision

Propose the following rules:

- Application persistence stores only opaque/encrypted records.
- Private keys, live cryptographic key handles, and platform keystore objects are not representable in the application record contract.
- The Rust core owns the storage contract and validates record size, owner identifiers, schema version, and non-empty ciphertext before persistence.
- Storage implementations are behind a `RecordStore` trait; physical storage technology remains undecided.
- Deletion is exposed as an explicit operation returning a non-secret `DeletionReceipt`.
- Recovery state is explicit. New writes fail closed while recovery is required; unavailable storage fails closed for reads/deletes.
- Schema versioning is part of the record contract, but no concrete serialization format is selected by this ADR.
- The deterministic `MemoryRecordStore` exists only for contract tests and is not a production persistence engine.

## Security boundaries

Storage must not become a private-key repository.

Storage records may contain ciphertext and non-secret metadata needed for addressing, schema validation, and lifecycle management. Keys remain inside the reviewed key-management boundary.

UI, mesh, and transport modules do not receive direct access to storage internals.

## Recovery and deletion

This ADR does not yet choose between database transactions, filesystem durability, encrypted backups, secure erase, tombstones, or retention windows.

Those mechanisms require evidence and approval in the final local-storage decision and must be compatible with ADR-0009 and ADR-0010.

## Rejected choices at this stage

No specific database or serialization format is accepted merely because it is convenient for Android or KMP.

No backup/recovery format is accepted before threat-model and migration review.

## Acceptance gate

Before this ADR becomes Accepted:

1. Concrete persistence technology and support lifecycle are reviewed.
2. Deletion guarantees and recovery semantics are documented for Android-first deployment.
3. Compatibility with ADR-0009 key management is verified.
4. Compatibility with ADR-0010 serialization is verified.
5. Negative-path and migration tests are present.
6. Security and threat-model review evidence is recorded.
7. CI demonstrates reproducible contract/integration tests.
