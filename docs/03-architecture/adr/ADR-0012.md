# ADR-0012 — Transport Architecture

**Status:** Proposed — Decision Pending Review  
**Date:** 2026-10-04  
**Related ADRs:** ADR-0008, ADR-0010, ADR-0011

## Context

Eagle requires a transport boundary for PrivateMesh and future platform adapters without allowing transport code to interpret application plaintext or cryptographic secrets.

The existing planning record does not approve a concrete channel, discovery mechanism, retry policy, or wire serialization format. This ADR therefore defines only the boundary and deterministic lifecycle contract.

## Decision

Propose the following rules:

- Transport accepts and returns opaque `TransportFrame` values only.
- A transport frame contains framing metadata plus already-protected/opaque payload bytes.
- Transport code must not receive application plaintext, private keys, or cryptographic key handles.
- Transport lifecycle is explicit: Disconnected → Connected → Closed, with closing/error behavior represented by typed states.
- Transport implementations are behind a `SecureTransport` trait.
- Concrete sockets, discovery, background scheduling, retry policy, multipath behavior, and platform channels remain adapter decisions.
- Serialization/wire encoding remains governed by ADR-0010 and is not implemented by this contract.
- `MemoryTransport` exists only for deterministic boundary tests.

## Security boundaries

Required flow remains:

plaintext → approved crypto/protocol layer → opaque/encrypted frame → transport → peer transport → protocol/crypto → plaintext

Transport is therefore below the protocol boundary. It may move opaque bytes and framing metadata but must not become a decryption or application-routing layer.

## Failure and lifecycle semantics

The contract fails closed when a caller sends or receives while disconnected, closing, or closed.

Frame size and payload-length consistency are validated at the transport boundary through the existing protocol contract.

## Rejected choices at this stage

No specific Bluetooth, Wi-Fi Direct, TCP, QUIC, WebRTC, relay, discovery, or mobile background strategy is accepted by this ADR.

No reliability or retry semantics are accepted until threat-model, battery/background, and protocol evidence are available.

## Acceptance gate

Before this ADR becomes Accepted:

1. Concrete transport channels are evaluated against Android lifecycle and background constraints.
2. Reliability/retry and duplicate-delivery semantics are documented.
3. Compatibility with ADR-0008 protocol and ADR-0010 serialization is verified.
4. Mesh/transport boundaries are tested to reject plaintext exposure.
5. Failure-injection and lifecycle tests are present.
6. Security and threat-model review evidence is recorded.
7. CI demonstrates reproducible contract tests.
