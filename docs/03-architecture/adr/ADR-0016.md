# ADR-0016 — Storage / Recovery Contract

**Status:** Proposed — Decision Pending Review  
**Date:** 2026-10-04  
**Related ADRs:** ADR-0009, ADR-0010, ADR-0011, ADR-0015

## Context

Eagle needs a stable storage boundary that platform adapters can implement without turning persistence into a key-management boundary. ADR-0011 remains the broader local-storage decision record; this ADR narrows the next gate to the deterministic record, recovery, and deletion contract that a SecureStorage adapter must honor.

The contract must remain independent of a database, filesystem, backup provider, encryption-at-rest format, serialization format, key-management scheme, or cryptographic implementation.

## Decision

Define the pre-crypto storage contract as follows:

1. The Rust security boundary owns the authoritative storage contract. Platform adapters implement that contract but do not reinterpret its security semantics.
2. Persistent application data is represented as an opaque encrypted record plus non-secret lifecycle metadata: record identifier, schema version, owner identifier, ciphertext, and creation timestamp.
3. Private keys, live cryptographic key handles, keystore objects, and plaintext application payloads are not representable through the storage record contract.
4. The contract exposes explicit put, get, and delete operations. Deletion returns a non-secret receipt containing only the record identifier and schema version.
5. Storage lifecycle is explicit: Healthy, RecoveryRequired, and Unavailable.
6. In RecoveryRequired, new writes fail closed. Reads and deletes follow the explicitly defined recovery contract and must not fabricate or silently replace security state.
7. In Unavailable, reads, deletes, and writes fail closed.
8. Record validation is mandatory before persistence: owner identifier must be present and bounded, ciphertext must be non-empty and bounded, and the schema version must be supported.
9. Schema versioning is part of the contract. This ADR does not select a serialization format or migration mechanism.
10. A deterministic in-memory store is test scaffolding only and is not a production persistence engine.

## Recovery semantics — deliberately independent of encryption/key shape

Recovery is a lifecycle contract, not a cryptographic design.

The recovery state machine describes storage conditions such as **missing, corrupted, moved/restored, or revoked/unusable state** without defining the shape, algorithm, wrapping mechanism, or ownership model of any cryptographic key. The storage layer reports the condition; a later key-management/crypto decision determines how security material is obtained, validated, rotated, or reconstructed.

Therefore ADR-0016 does not need to know whether keys are hardware-backed, software-backed, wrapped, derived, rotated, or otherwise managed. Those decisions remain outside this contract.

RecoveryRequired is a security-relevant state, not a transient logging condition. Implementations must not silently downgrade to an alternate storage path, recreate missing state with fabricated security metadata, or report success while the authoritative storage boundary is unavailable.

Transition out of RecoveryRequired requires an explicit successful recovery operation performed by the owning storage implementation. Unavailable remains fail-closed until the implementation can truthfully provide the required storage operations.

## Deletion semantics

Delete is explicit and observable at the contract layer. This ADR does **not** decide:

- cryptographic erasure;
- tombstones or tombstone retention;
- forward secrecy or treatment of historical encrypted records.

These are open questions for the applicable later ADR(s), together with backup-copy behavior, retention, secure media erasure, and recovery-after-delete semantics.

A successful delete means only that the record is no longer present through the authoritative store interface. It is not, by itself, a claim about copies outside that interface or about cryptographic erasure.

## Explicit out-of-scope decisions

This ADR explicitly does **not** decide:

- **Crypto:** no cryptographic algorithm, primitive, encryption mode, key wrapping, or encryption-at-rest scheme.
- **Key management:** no key lifecycle, keystore technology, key derivation, backup key, rotation, recovery key, or private-key representation.
- **Serialization:** no wire/storage encoding, serializer, canonicalization format, or migration mechanism; see ADR-0010.
- **Storage backend:** no database, filesystem, object store, provider, caching backend, or concrete SecureStorage implementation; see ADR-0011.
- **Backup/restore:** no backup provider, archive format, retention period, or restore authorization policy.
- **Secure deletion:** no media-erasure guarantee, cryptographic-erasure guarantee, or forensic non-recoverability claim.

Those choices remain gated by the applicable ADRs and executable evidence.

## Acceptance and review gate

Before this ADR becomes **Accepted**:

1. The SecureStorage Rust interface is reviewed against this contract.
2. Recovery and deletion behavior has executable negative-path tests.
3. Platform adapter responsibilities and failure propagation are documented.
4. Compatibility with ADR-0009 and ADR-0010 is verified without promoting either decision.
5. Security review confirms that no key material or plaintext crosses the storage boundary.
6. CI provides reproducible contract evidence for the selected implementation.

### Review authority

Acceptance requires **two explicit human approvals**:

- one architecture/domain reviewer; and
- one independent security reviewer who did not author the decision under review.

No single approval is sufficient. No automated green CI result substitutes for either approval.

### Review lifecycle

- While any required approval is missing, the ADR remains **Proposed**.
- There is **no automatic acceptance by timeout** and no silent acceptance through inactivity.
- After 14 days without completing the required review, the review issue is marked **stale/escalation required**.
- After 30 days without resolution, the ADR is marked **Review Stalled** and must be explicitly renewed, superseded, or withdrawn; it does not become Accepted.
- If a substantive objection is raised, status remains Proposed until the objection is resolved or the decision is explicitly withdrawn/superseded.

Until these conditions are satisfied, ADR-0016 does not authorize production storage implementation.
