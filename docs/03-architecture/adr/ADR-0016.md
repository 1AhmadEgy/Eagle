# ADR-0016 — Deterministic Token Bucket Rate Limiter

**Status:** Implemented in Android/JVM test runtime; build verification pending  
**Date:** 2026-10-04

## Context

Eagle requires deterministic throttling for security-sensitive operations. The repository now has a minimal Android application and JUnit runtime, so the previously specification-only Token Bucket can be implemented without inventing a new platform.

## Decision

Implement the first Token Bucket as a small Kotlin security primitive under:

`app/src/main/java/com/eagle/app/security/TokenBucket.kt`

The implementation:

- uses caller-supplied monotonic milliseconds;
- uses integer microtokens rather than floating-point decisions;
- uses checked/saturating behavior through `BigInteger` for refill multiplication;
- clamps balance to capacity;
- rejects non-positive costs and costs above capacity;
- treats backward time deltas as zero elapsed time;
- synchronizes state transitions;
- keeps the limiter independent from AI/ML.

JUnit vectors are implemented in:

`app/src/test/java/com/eagle/app/security/TokenBucketTest.kt`

## Security boundary

`request -> TokenBucket -> allow/limit -> operation`

Telemetry/risk analysis is downstream and cannot override the limiter.

## Why custom code here

This primitive is intentionally small and deterministic. A third-party rate-limit dependency would add a dependency and policy surface without evidence that Eagle needs distributed/shared state at this stage.

A distributed limiter is explicitly deferred. If Eagle later requires multi-process or network-wide quotas, that design requires a separate threat model and ADR.

## Verification status

The code and tests are committed to the working branch.

A local build could not be executed in the current tool environment because repository network access is unavailable, and the repository does not contain a Gradle Wrapper. GitHub reports no combined status for the implementation commit at the time of this record.

Therefore this ADR does **not** claim build/test PASS.

## Promotion gate

Before marking this implementation verified:

1. run the repository's Gradle verification gate;
2. run unit tests and lint;
3. confirm the test vectors;
4. benchmark the synchronized implementation;
5. evaluate bucket cardinality/eviction once bucket storage is introduced;
6. review whether the limiter belongs in the eventual Rust Security Core rather than remaining Kotlin-only.

## Follow-up

The next security primitive should be replay/freshness state, not ML. It must use deterministic nonce/sequence/freshness checks and remain independent from the limiter.
