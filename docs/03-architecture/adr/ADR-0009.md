# ADR-0009 — Key Management

**Status:** Proposed — Decision Pending Review  
**Date:** 2026-10-02  
**Related ADRs:** ADR-0007, ADR-0008

## Context
Define generation, protection, lifecycle, rotation, revocation, recovery/migration, and platform abstraction for long-lived identity keys and session keys.

## Candidate approaches
- Android Keystore: evaluate API-level support, hardware-backed/StrongBox availability, attestation, and testability.
- Maintained crypto library abstraction: evaluate primitives, platform integration, key boundaries, maintenance, and provenance.
- External native implementation: evaluate JNI/native boundaries, memory handling, extraction risks, maintenance, and provenance.

## Non-negotiable constraints
- private keys do not cross public module boundaries
- UI does not access private keys
- storage does not become a private-key repository
- cryptographic choices follow the accepted protocol ADR

## Decision
Pending review. No concrete library or hybrid design is approved by this draft.

## Required acceptance evidence
Selected key-storage model; supported Android API range; threat assumptions; failure/recovery behavior; testability strategy; migration impact.

## Research update — 2026-10-05

Primary platform evidence adds the following constraints.

### Android
Android Keystore can keep key material non-exportable and can enforce key-use restrictions. Where supported, StrongBox provides a stronger isolated hardware-backed environment. The Eagle abstraction must therefore distinguish at minimum:

- key handle/reference versus exportable key bytes;
- hardware-backed versus software-backed custody;
- user-authentication-required versus unattended/background use;
- attestation evidence versus mere local key presence;
- deletion/replacement semantics.

### Apple
Apple documents the Secure Enclave as a hardware-based key manager in which plaintext private-key material is not exposed to the application. Current Secure Enclave restrictions include hardware requirements and a restricted key algorithm/profile surface; Secure Enclave keys are generated there and are not a general-purpose import/export container.

Therefore Eagle must not define one lowest-common-denominator raw-private-key abstraction across platforms. Platform adapters should expose constrained cryptographic operations or opaque key references where possible.

### Supply-chain controls
Once a Rust crypto/key-management dependency is introduced, the dependency gate must include vulnerability, license, source provenance, duplicate-version, and update review. RustSec documents cargo-audit for advisory checking and cargo-deny for vulnerability/license/source policy.

### Current decision impact
This evidence does not select a concrete implementation. It does, however, rule out an architecture in which platform code exports long-lived private keys into generic shared storage or into the Rust/KMP public API as byte arrays.
