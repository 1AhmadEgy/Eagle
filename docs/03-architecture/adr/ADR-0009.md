# ADR-0009 — Key Management

**Status:** Decision package completed — final implementation approval pending evidence — Decision Pending Review  
**Date:** 2026-10-02  
**Related ADRs:** ADR-0007, ADR-0008

## Context
Define generation, protection, lifecycle, rotation, revocation, recovery/migration, and platform abstraction for long-lived identity keys and session keys.

## Candidate approaches
- Android Keystore: evaluate API-level support, hardware-backed/StrongBox availability, attestation, and testability.
- Maintained crypto library abstraction: evaluate primitives, platform integration, key boundaries, maintenance, and provenance.
- External native implementation: evaluate JNI/native boundaries, memory handling, extraction risks, maintenance, and provenance.

## Non-negotiable constraints
- private keys do not cross public module boundaries
- UI does not access private keys
- storage does not become a private-key repository
- cryptographic choices follow the accepted protocol ADR

## Decision
Pending review. No concrete library or hybrid design is approved by this draft.

## Required acceptance evidence
Selected key-storage model; supported Android API range; threat assumptions; failure/recovery behavior; testability strategy; migration impact.

### Decision boundary

Eagle adopts the Signal Protocol family as the one-to-one cryptographic reference, with PQXDH for session establishment and Double Ratchet for message-key evolution. This is a protocol decision, not a license or dependency approval.

libsignal remains reference/conformance material until Eagle completes license, support, API, platform, provenance, and integration review for the exact dependency/version.

No custom cryptographic primitive or bespoke ratchet is permitted.

### Evidence boundary

Design-level completion is recorded. Executable implementation, conformance tests, interoperability tests, independent cryptographic review, and production release authorization remain evidence gates and are not marked passed without real evidence.
