# ADR-0008 — Cryptographic Protocol

**Status:** Proposed — Decision Pending Review  
**Date:** 2026-10-02  
**Related ADR:** ADR-0007

## Context
Evaluate an E2E protocol for asynchronous and unreliable transports against asynchronous delivery, forward secrecy, post-compromise security, device lifecycle, future multi-device/group requirements, mobile constraints, auditability, and maintenance.

## Candidate families
- Signal-family protocols: evaluate async messaging, ratcheting, runtime/library support, maintenance, licensing, and multi-device model.
- Noise framework: evaluate authenticated handshakes plus the additional session/message-ratcheting layer Eagle would need.
- MLS (RFC 9420): evaluate group messaging, Android integration, 1:1 overhead, asynchronous delivery, and implementation maturity.
- Custom protocol: exceptional-risk path requiring strong justification and independent review.

## Decision criteria
Async messaging; forward secrecy; post-compromise security; mobile suitability; multi-device model; group roadmap; maintenance; supply-chain provenance; auditability.

## Decision
Pending review. No protocol is approved by this draft.

## Constraint
Do not implement custom cryptographic protocol logic solely from this planning draft.

## Research update — 2026-10-05

The candidate evaluation was expanded using current primary sources.

| Candidate | What it solves well | Eagle-specific advantages | Eagle-specific risks / blockers |
|---|---|---|---|
| Signal family (PQXDH + Double Ratchet + Sesame-style session management / current libsignal) | 1:1 asynchronous encrypted messaging, ratcheting, multi-device session management; current Signal specifications cover PQXDH, Double Ratchet and asynchronous multi-device session management | Closest conceptual fit for 1:1/offline messaging; current libsignal implementation is Rust-based with Java/Swift/TypeScript-facing bindings | Current libsignal README says use outside Signal is unsupported and the repository is AGPLv3; API/bridge layers are subject to change. Legal/licensing and product-compatibility review are mandatory before considering direct reuse |
| Noise framework | Authenticated handshakes and secure channel establishment primitives | Small conceptual core; can fit a P2P transport architecture and custom device identity model | Noise is a framework, not a complete asynchronous messaging system. Eagle would still need message/session state, replay, multi-device lifecycle, ratcheting, persistence/recovery, and group semantics |
| MLS / RFC 9420 + OpenMLS | Group membership, epochs, proposals/commits, group key schedule, forward/post-compromise properties at the group layer | Strong fit for future large-group E2EE and explicit membership/epoch evolution; OpenMLS is Rust and currently has a maintained 0.9.0 line | 1:1 path may carry unnecessary group-state complexity; platform targets including Android/iOS are currently built but not tested by OpenMLS CI; integration/storage/FFI and offline P2P semantics still require Eagle-specific engineering and audit |
| Custom | Full control over every Eagle-specific requirement | No external protocol constraints | Exceptional-risk option; requires formal cryptographic design, proofs/analysis, test vectors, independent review and long-term maintenance. Not acceptable as a shortcut |

### Findings that are now mandatory decision inputs

1. **Asynchronous/offline is first-class.** Signal's Sesame model explicitly addresses offline delivery, device sets, simultaneous session initiation, state rollback/restore, message loss, reordering and duplication. This is directly relevant to Eagle's P2P-only threat model even though Sesame itself assumes a server-backed mailbox architecture.
2. **Group epoch semantics are materially different from 1:1 ratchets.** MLS uses explicit epochs and proposal/commit sequencing; competing commits for the same epoch require an application-defined conflict-resolution rule.
3. **Replay cannot be inferred from encryption alone.** RFC 9180 explicitly states that HPKE does not provide general replay protection; sequence/order handling is an application concern.
4. **License and supportability are protocol-selection gates.** Reusing a mature implementation is preferred, but a dependency that is unsupported for external products or imposes an incompatible license cannot be treated as a production authority.
5. **No dependency is authoritative until provenance, release policy, supported targets, test coverage, security advisories, and update cadence are recorded.**

### Current non-decision

**No candidate is approved yet.**

The current evidence suggests a likely architectural split worth evaluating formally: Signal-family machinery for 1:1 asynchronous sessions and a group protocol such as MLS for large groups. However, that is only a research hypothesis; it must not be implemented until the team resolves cross-protocol identity binding, device lifecycle, message routing, state persistence, transcript/key separation, and a single coherent downgrade/replay policy.
